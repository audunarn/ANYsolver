# Early supporting review — pressure/history event route

Read-only, same-family source review at baseline `3ba94fe3`, before the author's early candidate checkpoint. No numerical execution or engineering acceptance.

## Three consequential design requirements

1. **Only coupled accepted states define pressure events.** The normal `z` is a nonlinear shared P1 unknown, while the friction law computes interpolated pressure from `z_i/S_i` and releases at zero (`s3_sliding_friction.py:443-460`). A midpoint evaluated with interpolated endpoint `z`, a geometry-only probe, or a Newton iterate cannot establish a real release/rebirth. Each physical subincrement that changes history needs a converged coupled q/z state at its own actual controls and loads, plus the same normal complementarity, equilibrium, physical gap, work and refusal gates as a user step. A finite set of equilibrated probes demonstrates particular events; it does not certify event absence between them without an additional justified rule.

2. **Commit the coupled state transactionally.** The existing monolithic driver validates a friction successor, commits structural state, commits friction, then performs recovered assembly and builds the step record (`static_path.py:1006-1029`). The semismooth path evaluates disposable material trials from committed state (`semismooth_path.py:112-147`) and line-search/branch probes (`:307-376`). A new subincrement route must preserve the committed origin through all probes and cutbacks, and either prepare recovery/report before both commits or restore both structural/contact state if any postcommit operation fails. No accepted history update may occur at an iterate, pressure acceleration or event locator.

3. **Subincrement identity needs a separate restart representation.** Current restart checks that checkpoint target equals `program.target_at(accepted_step)` and `len(previous_steps)==len(history)==accepted_step` (`static_path.py:811-821`). Inserting physical subincrements as ordinary numbered steps would change targets and break this contract. Bind macro user step, exact control fraction/stage, coupled q/z and structural/friction state, event policy and method to a new exact profile and checkpoint identity. Fresh restart must continue from the accepted physical subincrement without replaying or resealing an old geometry-only checkpoint. Sum work by accepted physical subincrement: material-relative elastic storage, Coulomb dissipation, release, projection loss and normal-variation numerical work are distinct; endpoint traction×gap proxies are not path-integrated work.

The old hard, endpoint-only weak and whole-chord geometry-only profiles remain separate. This note poses design conditions; no new candidate or event evidence had yet been inspected.

## Early checkpoint disposition

The author's `EARLY_CHECKPOINT.md` proposes an exact opt-in subtype with required positive integer `physical_subincrements_per_user_increment`, expanding the existing control/load program and solving every physical substep through the coupled semismooth owner. This is a defensible finite-resolution *development* convention if original program plus ratio are bound in the restart identity and the result distinguishes physical step count from completed user increment and fraction. The checkpoint correctly disclaims a continuum event-free proof. Its `a*d/2=2^-16 m` geometric opening is a prospective fixture discriminator, but the actual equilibrated interior pressure must establish release; the disclosed structural K/compliance seed is code verification rather than an independent nonlinear response reference.

The transaction requirement extends through public return. In the current driver, after structural/friction commits (`static_path.py:1008-1013`) it still performs recovery, record/snapshot construction (`:1014-1071`), final state preparation/sealing (`:1885-1898`), result/checkpoint serialization and return (`:1899-1967`). Moving recovery before commit would not by itself protect an exception or cancellation during these later operations. The new route needs a clear publication/rollback boundary for both structural and material state and an injected postcommit-return failure check. Existing trial cleanup cannot be assumed to undo committed generations or friction history.

This is a finite-resolution sequence of actual coupled substep solves, not an event-free guarantee. Installed response/history evidence remains pending.

**Actionable publication boundary defect:** `static_path.py:2004-2010` calls `_run_with_nonlinear_state_cleanup(lambda: guarded_invocation(run))` inside the outer runtime lease. The new `guarded_invocation` restores owner pose/history/summary/normal pressure only when `run()` raises (`s3_friction_history_path.py:28-38`). But `_run_with_nonlinear_state_cleanup` can raise from its `finally` *after* the guarded call returns (`nonlinear_state.py:261-287`), and the runtime lease can fail during exit after cleanup. Those exceptions occur after the history guard's context and rollback have ended. To support the stated after-commit through-public-return rollback, enclose cleanup and lease exit in the same publication guard (or an equivalent outer transaction), with an injected post-return finalizer failure test. Source's owned scalar mapping (`static_path.py:880-882`) avoids persistent structural generation advancement but does not extend the owner guard's lifetime. This finding was sent to author and lead before numerical execution.

**Endpoint work math checked:** The new report (`s3_friction_history_path.py:41-65`) uses the same current returned material anchor and complete q work map as friction residual assembly. Since `residual=-Σ area Deᵀ traction`, and traction is tangential, `-force·du=Σ area[traction·P(Js−Jt)du−gap*traction·Dn du]`; `material_relative_endpoint_contraction_j + numerical_normal_variation_endpoint_contraction_j` matches this identity. The names and `work_reporting_scope='endpoint_contractions_not_path_integrals'` are appropriately narrow. They do not measure integrated work or prove absence of pressure switching between the accepted equilibrated substeps.

**Publication repair observed:** Current `static_path.py:2008-2017` instead wraps `leased_operation` in `guarded_invocation`; `leased_operation` encloses the runtime lease and `_run_with_nonlinear_state_cleanup(run)`. Because `register_entry` remains inside `run` while the guard's context is live, a cleanup-finalizer or lease-exit exception now reaches the rollback handler with the owner retained. This resolves the earlier source-level nesting defect. Actual injected postcommit/outer-finalizer failure and cancellation evidence is still required before claiming the behavior was verified.
